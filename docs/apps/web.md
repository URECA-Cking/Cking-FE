# Web 앱

## 현재 구조

Web과 Creator 기능은 `apps/web/src/`에 있으며 독립 Web workspace에서 빌드·실행한다. Web 화면은 `apps/web/src/pages/`, Creator 운영 기능(이벤트·일정 관리)은 내 스페이스 화면과 `apps/web/src/components/creator/`에 있다. 루트에서는 `npm run dev:web`, `npm run build:web`, `npm run lint:web`로 Web workspace를 실행·검증한다.

### 책임과 라우트

| 영역 | 현재 라우트 | 책임 |
| --- | --- | --- |
| 인증 | `/login`, `/oauth/callback` | Google/Kakao OAuth 시작과 Login Code 교환 |
| 프로필 | `/profile/edit` | 팬의 닉네임·프로필 사진 편집, 닉네임 미설정 팬의 최초 설정. 크리에이터는 공개 프로필이 활동명·스페이스 사진이라 스페이스 편집으로 안내한다 |
| 사용자 | `/`, `/explore`, `/my-entries`, `/my-winners`, `/notifications`, `/my-page`, `/my-calendar`, `/my-tickets` | 탐색, 응모, 알림, 개인 정보·캘린더·당첨·응모권 관리 |
| 온보딩·공개 Space | `/onboarding`, `/onboarding/creators`, `/creators/:creatorId`, `/space/:slug`, `/events/:eventId` | 관심 분야·추천, 팔로우, Creator Space, 이벤트·응모 |
| Creator 운영 | `/creator/events/new`, `/creator/events/:eventId/edit` | 이벤트 작성·수정. 이벤트 목록·일정 관리는 내 스페이스의 이벤트·캘린더 탭에서 한다 |

`/studio*`는 내 스페이스로 리다이렉트한다. `/space/:slug`는 비로그인 공개 조회를 허용한다. 그 밖의 사용자 경로는 `RequireUser`, Creator 운영은 추가로 `RequireRole role="creator"`를 사용한다.

크리에이터 스페이스의 탭 선택은 현재 방문 기록 항목의 라우터 상태에 보관한다. 홈에는 마감되지 않은 이벤트만 미리 보여주고, 종료된 이벤트와 공개 결과는 이벤트 탭의 기존 카드에서 이벤트 상세로 이동해 확인한다. 상세 화면에서 화면 또는 브라우저 뒤로 가기로 돌아오면 마지막으로 선택한 탭을 유지한다. 개인 결과는 기존 `내 응모`와 `내 당첨` 화면에서 계속 조회한다.

`MainLayout` 안에서 링크·버튼으로 새 화면에 진입하면 공용 스크롤 컨테이너를 최상단으로 옮기고, 스크롤로 바뀐 헤더·하단 메뉴 표시 상태를 기본값으로 되돌린다. 현재 하단 메뉴를 다시 누를 때만 현재 history 위치도 최상단으로 초기화한다. 브라우저·화면의 뒤로 가기(`POP`)는 SPA 세션 동안 history 위치별로 기록한 스크롤 위치를 복원하며, 비동기 콘텐츠가 늦게 늘어날 때는 1px 허용 오차와 제한된 프레임 안에서 재시도한다. 복원 대기 중 사용자가 휠·터치로 스크롤하면 사용자의 입력을 우선한다. 위치 기록은 최근 100개 history 항목으로 제한한다. modifier/휠 클릭으로 하단 메뉴를 새 탭에서 열 때는 현재 탭의 상태를 바꾸지 않는다.

알림 목록은 서버의 `readAt`으로 읽음 상태를 표시한다. 읽지 않은 항목은 배경·제목·표식으로 강조하고, 읽음 처리 중에는 목록과 헤더 배지를 함께 갱신한다. 진행 중인 조회가 늦게 끝나도 낙관적 읽음 값과 서버에서 확정된 읽음 값이 카드·배지에서 덮어써지지 않도록 유지한다. 헤더는 첫 100건만 조회하고 알림 화면의 첫 다섯 페이지(20건씩)와 결과를 공유한다. 100건을 넘는 목록에서는 배지 개수를 하한값(`N+`)으로 표시하며, 첫 100건이 모두 읽혔으면 뒤쪽의 미확인 알림 유무는 알 수 없다. 정확한 전체 미확인 개수는 BE 전용 조회 API가 필요하다. '모두 읽음'은 서버의 전체 읽음 API를 호출하며, 실패하면 화면 상태를 되돌리고 다시 조회한다. 전체 읽음은 성공했지만 후속 조회가 실패하면 읽음 상태를 유지하고 최신 목록을 확인하지 못했다고 안내한다. 새로고침·재접속 시에도 서버 상태를 다시 조회한다.

최초 당첨·재추첨 당첨·최초 추첨 미당첨 결과 발표 알림은 서버의 제목·본문을 표시하고, 유형별 문구와 아이콘으로 구분한다. 항목을 누르면 기존 개별 읽음 처리 후 공개 결과가 표시되는 해당 이벤트 상세(`/events/:eventId`)로 이동한다. 이벤트가 연결되지 않은 제재 알림은 읽음 처리만 한다.

홈의 설치 안내(`InstallBanner`)는 기본으로 접혀 "Cking을 앱처럼 쓰기" 한 줄만 보이고, "설치 방법 보기"를 누르면 설명과 환경별 절차가 펼쳐진다. 브라우저가 바로 설치 팝업을 띄울 수 있는 환경에서는 같은 줄에 "앱 설치하기" 버튼을 바로 보여준다. 출석 카드는 최근 7일 도장을 7칸 스탬프로 보여준다(안 찍은 칸은 아래 그림자가 있는 3D 캡슐, 찍힌 칸은 핑크 채움, 오늘 찍을 칸은 링으로 강조하고 `aria-current="step"`을 붙이며, 마지막 칸은 보상 아이콘). 도장이 찍힌 칸에만 튀어 오르는 효과와 고리·반짝이를 주고, 모션을 줄인 환경에서는 애니메이션뿐 아니라 고리·반짝이 장식 요소도 그리지 않는다. 찍힌 칸의 완료 표시는 `FilledCheck`를 쓴다. 출석 완료·재시도·적립 규칙은 기존 공용 미션 API 계약을 그대로 따른다(칸마다 다른 보상은 없다). 완료 표시는 속이 찬 `FilledCheck`로 통일한다.

홈은 서버의 웰컴 퀘스트 상태(`eligible`, `completed`)로 신규 회원을 판별하고 FE가 가입 시각을 추측하지 않는다. 신규 회원(대상이고 아직 끝내지 않은 회원)에게는 응모 섹션 대신 웰컴 퀘스트(히어로·시작 가이드·OX 퀴즈), 출석 카드, 추천 크리에이터("지금 팬들이 가장 많이 모이는 곳")를 순서대로 보여준다. 시작 가이드를 닫으면 히어로와 가이드가 빠지고 출석 카드가 위로 올라오며, 닫은 상태는 회원별로 브라우저 저장소에만 남긴다(서버 저장 아님). STEP 1은 처음 표시될 때 회원당 한 번 자동으로 지급을 요청하고, STEP 2는 인기 크리에이터에서 실제로 팔로우한 뒤 퀘스트 상태를 다시 불러와 받는다. STEP 3의 정답은 FE가 판정하지 않고 고른 답을 서버에 보낸다. 마지막 단계를 받으면 그 화면에서는 완료 안내를 보여주고, 다시 들어오면 일반 홈으로 돌아간다. 웰컴 보너스는 세 단계와 독립이라 퀘스트가 끝난 뒤에도 받지 않았다면 출석 카드에 남는다. 도장 칸 아래 배지로 보여 주고(보너스는 출석 일수가 아니라 도장 칸에는 찍지 않는다), 출석 도장을 누르면 출석 뒤에 이어서 지급을 요청한다. 출석이 실패하면 보너스는 요청하지 않고, 이어 처리하는 동안 버튼은 "처리 중"으로 잠긴다. 출석 뒤 보너스를 기다리는 사이 로그아웃·계정 전환·화면 이동이 있으면 보너스를 요청하지 않는다. 지급 성공 뒤 헤더 응모권은 기존 갱신(`useMyTickets`의 `refresh`)으로 다시 조회한다. 승인 여부가 불확실한 지급 요청(`EARN_STATUS_UNKNOWN`, 응답 코드 없는 오류, 5xx 등)은 `requestId`와 최초 `answer`를 회원·단계별로 브라우저 저장소에 보존해, 새로고침이나 홈 재진입 뒤에도 새 UUID를 만들지 않고 같은 요청으로 복구하며 승인되거나 서버가 처리하지 않았다고 확정할 때만 지운다. 다른 `requestId`로 이미 선점됐다는 응답(`WELCOME_QUEST_ALREADY_CLAIMED`)은 서버가 승인 전(PENDING·EXECUTING)인 요청에도 줄 수 있어 완료로 단정하지 않고 상태를 다시 조회해 반영한다. 퀘스트 상태 조회가 실패하면 신규 여부를 알 수 없어 일반 홈이 보이므로, 홈 위쪽에 다시 시도 줄을 보여준다. 웰컴 퀘스트의 강조(앰버)·성공(초록) 글씨는 모드별로 대비를 맞춘 `warm-accent`·`success-text` 토큰을 쓰며, 값의 대비는 `apps/web/test/themeContrast.test.js`가 검증한다.

홈 로딩 성능: 라우트는 홈·로그인만 처음부터 불러오고 나머지 화면은 `React.lazy`로 처음 열 때 내려받는다(레이아웃 안에서는 페이지 영역만 로딩을 보여 준다). 홈은 팔로우한 크리에이터의 프로필만 쓰므로 이벤트 목록을 함께 받는 `loadCreatorDirectory` 대신 캐시된 프로필 목록(`getCreatorCatalog`)만 받고, 진행 중 이벤트는 첫 페이지의 `totalPages`로 나머지 페이지를 병렬로 받는다. 응모권 잔액은 홈에 보이는 응모 이벤트의 크리에이터 것만 조회한다. 진행 중 이벤트·프로필 목록·팔로우 소식·당첨 배너는 `useAsync`의 `cacheKey`로 마지막 결과를 먼저 보여 주고 뒤에서 갱신한다. 키가 바뀌면 이전 키의 결과를 바로 비우고, 회원별 결과는 키에 회원 번호를 넣으며 로그아웃 때 캐시를 모두 비운다. 캐시로 그린 화면은 뒤의 갱신이 실패해도 지우지 않고, 보여줄 데이터가 없을 때만 오류 화면으로 바꾼다. 같은 키의 요청이 시작 순서와 다르게 끝나도 더 늦게 시작한 요청의 결과를 오래된 요청이 덮어쓰지 못한다. 로그아웃으로 캐시를 비우기 전에 시작한 요청은 나중에 끝나도 캐시와 화면에 반영하지 않고, 조회가 비활성화되거나 조건이 바뀌면 이전 요청도 같은 방식으로 무효화한다. 캐시된 진행 중 이벤트는 마감 시각(`endAt`)을 현재 시각과 다시 비교해 끝난 이벤트를 응모 목록에서 뺀다(시각은 30초마다 갱신). 지연 로딩한 화면을 받지 못하면 `ChunkErrorBoundary`가 안내와 "다시 시도"(새로고침)를 보여준다. 잔액과 응모 여부는 화면 값이 틀려 보일 수 있어 캐시하지 않는다.

홈·탐색 표시 규칙: 이벤트의 정방형 미리보기(홈 응모 티켓 88×88, 탐색 이벤트 카드·내 응모 64×64)는 이벤트 배너 대신 Creator 프로필 사진을 쓴다. 탐색 Creator 카드는 응모권 잔액을 조회·표시하지 않고 `진행 중 n` 태그만 둔다. 탐색의 `더 보기` 목록(전체 크리에이터·검색 결과·맞춤 추천·이벤트 둘러보기)은 끝까지 펼치면 같은 자리의 `접기`로 처음 개수로 되돌린다. Creator 콘텐츠 태그 공개 API는 BE 문서상 FE 범위 밖이라 연동하지 않는다. 홈의 새 게시물처럼 `overflow-x-auto` 가로 스크롤 영역 안에 `sr-only`(absolute) 요소를 두면 스크롤 컨테이너에 `relative`를 지정한다. 지정하지 않으면 라벨이 컨테이너 밖 기준으로 배치되어 모바일에서 페이지 전체가 가로로 스크롤되며, `apps/web/test/newsFeedLayout.test.js`가 360~430px에서 문서 폭과 뷰포트 폭이 같은지 검증한다.

### 상태와 인증

`UserContext`가 `/api/me`, 세션 상태, 역할, 팔로우 상태를 관리한다. Access JWT는 `sessionStorage`에 두며, `apps/web/src/api/client.js`가 Web 전용 refresh와 401 동작을 처리한다. 공통 HTTP 전송과 토큰 저장소의 저수준 로직은 `packages/shared`를 사용한다. Toast는 `ToastContext`가 담당한다. Web 전용 상태·Context·페이지는 Admin과 공유하지 않는다.

회원·크리에이터 프로필 사진은 Web 공통 `ProfilePhoto`로 표시한다. 사진 URL이 없거나 이미지 로딩에 실패하면 사람 아이콘을 보여주며, URL이 바뀌면 새 사진을 다시 표시한다. 사진 업로드·저장과 Creator Space의 기본 이미지 URL 결정은 기존 API 흐름을 따른다.

Creator Space 게시물 상세는 작성자 이름과 작성 시각, 이미지, 본문, 좋아요, 댓글 목록·입력창 순으로 표시한다. 본문에는 작성자 이름을 반복하지 않고, 댓글은 상세를 열면 바로 조회한다. 좋아요와 댓글의 권한·오류 처리는 기존 게시물·댓글 API 흐름을 따른다. 게시글 주인(크리에이터)과 관리자는 같은 댓글창에서 남의 댓글에 "…" 메뉴의 "이 회원 차단"(그 스페이스에서 1~365일)과 삭제를 쓸 수 있고, 호출하는 API만 다르다(크리에이터는 크리에이터 API, 게시글 주인이 아닌 관리자는 관리자 API). 게시글 주인이 쓴 댓글(`writtenByCreator`)에는 차단 메뉴를 보이지 않는다. 작성자가 관리자인지는 댓글 응답으로 알 수 없어서 그 경우는 서버가 거절한 뒤 안내한다. 댓글을 등록·삭제하면 BE 응답에 갱신된 수가 없어, 성공 직후 목록 카드와 상세의 댓글 수를 보던 값에 ±1 해서 먼저 보여 주고(`postCommentCount.js`), 목록을 다시 받으면 서버 값으로 맞춘다. 실패하거나 이미 삭제된 댓글(404)이면 수를 바꾸지 않는다.

`apps/web`은 PUBLIC, USER, CREATOR API를 소유한다. 공통화 후보는 앱 독립적인 UI·HTTP 클라이언트·유틸·실제 공통 타입뿐이며, `UserContext`, 팔로우 상태, Web/Creator 화면은 shared에 두지 않는다. 관리자 콘솔은 `VITE_ADMIN_BASE_URL`로 독립 Admin 앱에 진입한다.

API 사용 범위와 정본 링크는 [api-coverage.md](../api-coverage.md)를 따른다.

### Creator Quiz 최종 문항 구성

내 Quiz 검토 시트에서 최신 미게시 Revision의 문항을 선택·재정렬·편집하거나 직접 추가한다. 최종 미리보기 후 저장하고 서버에서 받은 Revision을 다시 확인해 책임 승인한다. 게시 요청은 별도로 실행하며 AI 원본의 기존 Judge 승인 흐름은 유지한다.

원본 평가와 현재 수정 상태를 구분한다. 수동 문항에 근거가 없으면 근거 없음으로 표시하며 자동 AI 재평가를 하지 않는다. 최초 게시 이후에는 공개를 취소해도 편집할 수 없고 같은 고정 Revision만 재게시한다. 신규 필드가 없는 BE 응답에서는 편집 진입을 숨긴다.

편집 UUID·정규화 요청 본문·저장 결과는 Creator/Quiz별 별도 localStorage 키에 보관한다. Web Locks와 조건부 갱신으로 탭 간 요청을 보호하고 응답 유실은 같은 UUID·본문으로 복구한다. 저장소/Web Locks가 불가능하면 저장 요청을 보내지 않는다. stale 충돌에서는 작성 내용을 보존하고 최신본을 확인하며 사용자의 명시적 선택 없이 새 UUID로 저장하지 않는다. Generation/Judge 기록은 변경하지 않는다.

계약 정본은 [BE 문항 구성·책임 승인](https://github.com/URECA-Cking/Cking-BE/blob/develop/docs/domains/quiz/composition-api.md)이다. 실제 BE·Provider 통합 검증은 별도 승인 후 수행한다.

### 실행 환경과 회귀 검증

로컬에서 `VITE_API_BASE_URL`을 비우면 `/api`는 Web과 같은 출처로 요청되고 Vite가 `VITE_API_PROXY_TARGET`(기본 `http://localhost:8080`)으로 전달한다. OAuth 시작은 페이지 이동이므로 프록시를 거치지 않고 백엔드 주소로 직접 이동한다. `VITE_ADMIN_BASE_URL`은 독립 Admin 앱 주소이며, 운영 빌드에서 값이 없으면 이동 가능한 관리자 링크 대신 `서비스 준비 중` 비활성 항목을 표시한다. 개발 배포 빌드는 CI가 API와 Admin 주소를 주입한다.

모노레포 전환 후 Web 경계와 로컬 검증 결과는 [A-03 회귀 검증](../verification/a-03-web-regression.md)을 참고한다.

알림 화면은 카드를 왼쪽으로 밀어 "삭제"를 눌러 알림을 지운다(서버에는 숨김으로 기록하고 행은 남기며, 지운 알림은 되돌릴 수 없음). 조금 밀면 삭제 버튼이 드러나 눌러야 삭제하고, 카드 너비의 65% 이상 끝까지 밀고 놓으면 버튼 없이 바로 삭제한다(되돌릴 수 없어 기준을 크게 잡았다). 열린 카드는 Esc로 닫는다. 세로 스크롤과 당겨서 새로고침은 가로 이동일 때만 스와이프로 가져와 방해하지 않는다. 삭제한 알림은 목록·헤더 배지에서 바로 빠지고, 늦게 도착한 오래된 조회 응답에도 다시 나타나지 않는다.

### Quiz 수동 마감 (#245)

내 Quiz 목록과 검토 시트에서 마감 상태·시각을 표시한다. 기존 ConfirmSheet로 영구 마감을 확인하고 성공·상태 충돌 뒤 상세를 재조회한다. 마감 후 변경 명령과 팬 신규 제출은 차단하며 기존 정보·응시 결과 조회는 유지한다. 실제 dev 마감·제출 E2E는 테스트 계정과 폐기 가능한 Quiz로 별도 검증한다. API 계약 정본은 [BE Quiz API](https://github.com/URECA-Cking/Cking-BE/blob/develop/docs/domains/quiz/api.md)다.

### 이벤트 상품 키 자동 생성 (#247)

이벤트 생성·수정 폼의 상품 키 입력은 숨기고 신규 상품 행에만 자동 발급한다. 기존 상품 키와 현재 폼에서 삭제한 키는 재사용하지 않는다. 상품명·순위·가중치·수량 입력과 기존 priority 초기값 계산 및 API 계약은 유지한다. 실제 BE 변경 API 검증은 별도 테스트 이벤트로 진행한다.
